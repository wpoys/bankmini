## 1. Arsitektur *Style* Perangkat Lunak

Gaya arsitektur yang diterapkan pada proyek BANK MINI adalah **arsitektur berlapis (*Layered / N-Tier Architecture*)** yang dipadu dengan pola **MVC (*Model-View-Controller*)** dari framework Laravel. Pemisahan dilakukan berasas *Separation of Concerns*, dengan ciri **berlapis longgar (*loosely layered*)**: setiap lapisan memiliki tanggung jawab yang jelas, tetapi tidak semua akses wajib melewati seluruh lapisan. Dalam praktiknya, controller dapat memanggil model Eloquent secara langsung untuk pembacaan data atau kebutuhan sederhana, sedangkan service di `app/Support` dipakai untuk logika bisnis yang kompleks (mis. transaksi keuangan, penerbitan nomor, dan proses OTP). Contohnya, `Accounting\LaporanController` menerima model `Nasabah`/`Transaksi` dan menyusun laporan tanpa perantara service.

| Lapisan | Implementasi dalam Proyek |
|---|---|
| **Lapisan Presentasi (*Presentation*)** | Template Blade di `resources/views` (`admin`, `teller`, `supervisor`, `nasabah`, `transaksi`, `jadwal`, `notifikasi`, `permintaan-pin`, `verifikasi-harian`, `auth`, dll.) untuk web; respons **JSON** dari `routes/api.php` untuk aplikasi mobile; struk **PDF** (DomPDF) |
| **Lapisan Akses HTTP** | Route (`routes/web.php`, `routes/api.php`) + Middleware: `CheckActiveUser` (`check.active`), `EnsureActiveApiUser` (`check.active.api`), `RoleMiddleware` (`role`), `auth`, `auth:sanctum`, `guest`, dan `throttle` |
| **Lapisan Kontroler (*Controller*)** | `app/Http/Controllers/Admin`, `Teller`, `Supervisor`, `Nasabah`, `Accounting`, `Api`, `Auth` (plus controller akar seperti `StrukController`, `JadwalPetugasController`, `NotifikasiController`, `PermintaanPinController`, `ProfilController`, `VerifikasiHarianController`) — menerima request, memvalidasi, memanggil service/model atau langsung, lalu menentukan view/response |
| **Lapisan Bisnis (*Service / Business Logic*)** | Kelas di `app/Support`, mis. `NomorGenerator` (nomor rekening/struk), `PendaftaranNasabah`, `PermintaanPinService`, `ResetPasswordOtp`, `JadwalPetugasService`, `VerifikasiHarianService`, `VerifikasiHarianProses` |
| **Lapisan Akses Data (*Persistence*)** | 16 model Eloquent di `app/Models`: `Transaksi`, `Nasabah`, `JurnalAkuntansi`, `LaporanHarian`, `DetailLaporan`, `KoreksiTransaksi`, `RekonsiliasiKas`, `DetailRekonsiliasiKas`, `VerifikasiHarian`, `JadwalPetugas`, `Konfigurasi`, `NomorSequence`, `PermintaanResetPin`, `User`, `UserNotification`, `ActivityLog` |
| **Lapisan Data (*Database*)** | MySQL — basis data `bankukk` (`DB_CONNECTION=mysql`), skema dikelola **37 berkas migration** di `database/migrations` |

Aliran request pada umumnya berjalan dari atas ke bawah: **View/API → Route & Middleware → Controller → (Service) → Model Eloquent → Database**, lalu hasilnya dikembalikan ke lapisan presentasi. Tanda kurung pada *Service* menegaskan tahap ini opsional (sesuai sifat berlapis longgar). Keunggulan gaya ini: modul mudah diubah tanpa merusak bagian lain (menambah menu cukup menambah route + controller + view), mudah diuji, dan mudah dipelihara sesuai elemen unit "Mendefinisikan & Menyusun Struktur Perangkat Lunak".

## 2. *Data-Centered Architectures*

Sistem ini menerapkan arsitektur **berpusat pada data (*data-centered*)**: basis data relasional menjadi **komponen sentral**, dan seluruh komponen lain (Admin, Teller, Supervisor, Nasabah, serta aplikasi mobile) membaca atau mengubah data yang **sama** melalui aplikasi Laravel, bukan mengakses basis data secara langsung.

- **Komponen pusat:** basis data relasional yang memuat tabel inti `nasabah`, `transaksi`, `jurnal_akuntansi`, `laporan_harian`, `detail_laporan`, `rekonsiliasi_kas`, `detail_rekonsiliasi_kas`, `koreksi_transaksi`, `konfigurasi`, `activity_logs`, `user_notifications`, `verifikasi_harian`, `jadwal_petugas`, `permintaan_reset_pin`.
- **Komponen penunjang yang mengelilingi pusat:**
  - *Web client* (Blade) menulis dan membaca basis data; *mobile client* (REST API) **terutama membaca** data transaksi dan saldo (read-only) serta melakukan aksi terbatas (mis. login, ubah PIN, membaca notifikasi). Keduanya memakai aplikasi Laravel dan basis data yang **sama**.
  - **Layanan transaksi:** setoran/penarikan menulis ke tabel `transaksi`, **sekaligus** memperbarui saldo `nasabah` (increment/decrement) dan mencatat `jurnal_akuntansi` serta `activity_logs` dalam **satu transaksi basis data (ACID)**.
  - **Layanan pelaporan:** `laporan_harian` + `detail_laporan` **diturunkan** (*derive*) dari data transaksi, lalu diverifikasi oleh supervisor; `rekonsiliasi_kas` mencatat rincian pecahan kas fisik.
  - **Audit:** setiap aksi penting dicatat ke `activity_logs`.
- **Sifat arsitektur:** data dikelola terpusat dan redundansi diminimalkan (skema ternormalisasi), komponen tidak menyimpan status sendiri — keadaan terkini selalu diambil dari pusat data. Basis data menjadi satu-satunya sumber kebenaran (*single source of truth*) bagi web maupun API mobile, sehingga saldo di layar teller dan di aplikasi nasabah selalu konsisten.

## 3. Struktur Umum Rancangan Perangkat Lunak

Struktur umum sistem dibagi menjadi **modul-modul fungsional** dalam kerangka berlapis:

1. **Modul Autentikasi & Otorisasi** — login web (`Auth\LoginController`) dan API (`Api\AuthController`), session untuk web / token Sanctum untuk API, pemeriksaan peran via `RoleMiddleware` (Admin/Teller/Supervisor/Nasabah), status akun aktif/nonaktif (`CheckActiveUser`, `EnsureActiveApiUser`), serta reset password via OTP (`Auth\PasswordResetController`, `Api\PasswordResetController`, `Support\ResetPasswordOtp`).
2. **Modul Data Master** — pengguna (`Admin\UserController`, `Admin\PenggunaController`), nasabah termasuk **import massal** (template + preview + konfirmasi) dan **arsip/restore** (`Admin\NasabahController`, `Support\PendaftaranNasabah`, `Support\KodeJurusan`), konfigurasi sistem (`Admin\KonfigurasiController`, model `Konfigurasi`), jadwal petugas (`JadwalPetugasController`, `Support\JadwalPetugasService`).
3. **Modul Transaksi** — setoran/penarikan dengan validasi PIN (`Hash::check` terhadap `pin_keamanan` yang di-hash), cek nasabah terarsip, saldo cukup, **saldo minimum**, serta **konfirmasi H-1 untuk penarikan besar**; pencegahan **transaksi ganda** (`sudahDiproses`); nomor struk otomatis (`Support\NomorGenerator`); koreksi transaksi (`Teller\KoreksiController`, `KoreksiTransaksi`).
4. **Modul Akuntansi** — jurnal akuntansi dibuat otomatis saat transaksi (`Teller\TransaksiController::catatJurnal` untuk setoran/penarikan, `Support\PendaftaranNasabah::catatJurnal` untuk setoran awal, `Accounting\VerifikasiKoreksiController::catatJurnal` untuk koreksi), lalu ditampilkan/diekspor oleh `Accounting\JurnalController` (`JurnalAkuntansi`). Rekonsiliasi kas dicatat melalui rincian kas fisik pada `Teller\LaporanController` dan diverifikasi oleh `Supervisor\VerifikasiController`.
5. **Modul Pelaporan** —
   - laporan kas harian → `Teller\LaporanController` (index/create/store/show/submit);
   - verifikasi & audit → `Supervisor\VerifikasiController` (index/show/approve/reject/pending/audit);
   - laporan lanjutan → `Supervisor\LaporanController` (laporanHarian, bukuBesar, mutasiNasabah, saldoProduk, laporanTahunan) dan `Accounting\LaporanController` (panel, jurnal, mutasiNasabah, kartuSimpanan, saldoProduk, tahunan);
   - jurnal → `Accounting\JurnalController`;
   - Ekspor PDF memakai `barryvdh/laravel-dompdf` (DomPDF); ekspor Excel memakai `Support\XlsxWriter`, `Support\ExcelExport`, dan `Support\JurnalExcelExport`.
6. **Modul Notifikasi** — notifikasi dalam aplikasi (`user_notifications`, `NotifikasiController`, `Api\NotifikasiController`) dan email OTP (`Support\ResetPasswordOtp` via SMTP).
7. **Modul Keamanan & Audit** — PIN nasabah (di-hash), permintaan reset PIN (`PermintaanPinController`, `Support\PermintaanPinService`), serta activity log/audit trail (`ActivityLog`, `Supervisor\VerifikasiController::audit`).
8. **Modul Pemeliharaan** — backup basis data melalui `Admin\BackupController` (hasil di `storage/app/backups`); pemulihan (*restore*) dilakukan manual dari berkas backup.

**Struktur fisik (peta direktori):**

```
bankmini/
├── routes/                 web.php + api.php
├── app/Http/
│   ├── Controllers/        Admin, Teller, Supervisor, Nasabah, Accounting, Api, Auth
│   └── Middleware/         CheckActiveUser, EnsureActiveApiUser, RoleMiddleware
├── app/Support/            layanan bisnis (NomorGenerator, PendaftaranNasabah,
│                           ResetPasswordOtp, VerifikasiHarianProses, ExcelExport, dll.)
├── app/Models/             16 model Eloquent
├── resources/views/        Blade per modul (admin, teller, supervisor, nasabah, ...)
├── database/migrations/    37 berkas skema + perubahan skema (versi terkendali)
├── storage/app/backups/    hasil backup database
└── config/                 database, mail, queue, session
```

## 4. Sistem Terdistribusi (*Distributed Systems*)

Rancangan BANK MINI paling tepat dijelaskan sebagai aplikasi dengan pola **client–server**, bukan sistem terdistribusi penuh. Beberapa perangkat klien (browser dan aplikasi mobile) mengakses satu aplikasi Laravel melalui jaringan, namun aplikasi utama berjalan pada **satu simpul server**. Aspek **terdistribusi** baru menjadi jelas apabila komponen berikut ditempatkan pada **host yang berbeda**:

1. **Pola *client–server*:** server Laravel (Apache/Nginx + PHP-FPM) melayani banyak *client* secara bersamaan — browser PC Admin/Teller/Supervisor di jaringan LAN sekolah, dan aplikasi mobile nasabah yang mengakses **REST API** (`routes/api.php`).
2. **Dua antarmuka, satu aplikasi:** web (Blade, berbasis session) dan API mobile (JSON, token `auth:sanctum`) berbagi logika bisnis dan basis data yang sama — pola *multi-channel* pada satu sumber data.
3. **Basis data sebagai layanan (opsional pada host terpisah):** MySQL dapat berjalan sebagai layanan pada host yang sama maupun host terpisah; lokasi sebenarnya mengikuti konfigurasi *deployment* (`config/database.php`).
4. **Layanan eksternal:** pengiriman OTP memakai server SMTP (`config/mail.php`). Antrean pekerjaan (`jobs`) dikonfigurasi pada `config/queue.php` dengan koneksi saat ini **`sync`** (berjalan di dalam proses request); bila diubah ke `database`, antrean memakai basis data yang sama.
5. **Penanganan kegagalan antarproses:** *rollback* transaksi bila salah satu penulisan gagal, `throttle` untuk mencegah penyalahgunaan (login 5x/menit, OTP 3–5x/menit), serta pesan galat bila SMTP/DB tidak terjangkau — inilah unsur yang mendekati prinsip dasar sistem terdistribusi: konsistensi data dan penanganan kegagalan.

**Catatan:** banyak klien maupun adanya REST API saja tidak otomatis menjadikan aplikasi sebagai sistem terdistribusi; statusnya lebih tepat disebut *client–server* yang **siap dikembangkan** menjadi terdistribusi bila aplikasi, basis data, dan layanan email dipisah ke host berbeda.

## 5. *Database Architecture*

Arsitektur basis data yang diterapkan adalah **basis data relasional terpusat** dengan karakteristik:

- **Jenis & konfigurasi:** MySQL sebagai satu-satunya basis data aplikasi (basis data `bankukk`, `DB_CONNECTION=mysql` di `.env`), ditetapkan pada `config/database.php`.
- **Terdesain ternormalisasi:** setiap entitas punya tabel sendiri dengan kunci primer & asing, mis. `nasabah` (1) ↔ `transaksi` (N), `laporan_harian` (1) ↔ `detail_laporan` (N), `rekonsiliasi_kas` (1) ↔ `detail_rekonsiliasi_kas` (N), `transaksi` (1) ↔ `jurnal_akuntansi` (N). Kolom nominal uang bertipe `DECIMAL`/integer, dan diperkuat dengan *check constraints* (migrasi `2026_09_11_000002_check_constraints.php`): `transaksi.nominal > 0`, `nasabah.saldo >= 0`, `jurnal_akuntansi.jumlah > 0`, `rekonsiliasi_kas.total_fisik >= 0`.
- **Integritas & konsistensi:** proses yang mengubah data terkait dibungkus `DB::transaction` (ACID) — antara lain pada `Teller\TransaksiController::proses`, `Teller\LaporanController::store`, `Supervisor\VerifikasiController::approve`, `Accounting\VerifikasiKoreksiController`, `Admin\NasabahController` (store/arsip/restore), `Admin\UserController`, serta service `PendaftaranNasabah`, `PermintaanPinService`, `JadwalPetugasService`, `VerifikasiHarianProses`, dan `NomorGenerator`. Bila satu langkah gagal, seluruh perubahan *rollback*.
- **Pengelolaan skema:** perubahan struktur dilakukan lewat 37 *migration* berurutan (dari pembuatan tabel sampai penambahan `status_pending`, `konfigurasi`, check constraints, dll.), sehingga skema dapat direproduksi.
- **Komponen khusus:** tabel `nomor_sequence` menerbitkan nomor rekening (`KODE-JURUSAN-001`) dan nomor struk (`TRX-YYYY-NNNNNN`) secara atomik — baris *sequence* dikunci dengan `lockForUpdate` (`SELECT ... FOR UPDATE`) di dalam satu transaksi; tabel pendukung: `password_reset_otp`, `personal_access_tokens`, `jobs`, `sessions`, `cache`.
- **Keamanan data:** akses basis data dibatasi pada kredensial di `.env` (tidak di repositori publik), backup basis data melalui `Admin\BackupController` (hasil di `storage/app/backups`), pemulihan manual dari berkas backup; audit trail pada `activity_logs`.

## 6. *Data-Flow Architecture*

Aliran data pada sistem mengikuti pola **transformasi data (*transform-centered*)**: data masuk → divalidasi → diproses → disimpan → ditampilkan/diekspor. **Transaksi berjalan online (satu per satu)**, sedangkan **laporan harian berjalan batch (rekap periodik)**.

**Alur 1 — Transaksi setoran/penarikan (online):**

```
Input form Teller (web)
   → Validasi (login, role, PIN via Hash::check, saldo, saldo minimum,
                konfirmasi H-1, anti transaksi ganda)
   → Proses transformasi (hitung saldo baru, terbitkan nomor struk)
   → Penulisan (tabel transaksi + update saldo nasabah + jurnal_akuntansi
                + activity_logs — satu transaksi DB)
   → Output (halaman struk, cetak/unduh PDF via DomPDF, notifikasi ke nasabah)
```

**Alur 2 — Pelaporan harian (batch, periodik):**

```
Kumpulkan transaksi hari ini (filter tanggal, kas laci, teller)
   → Rekap & hitung total (detail_laporan) + rincian kas fisik (rekonsiliasi_kas)
   → Simpan laporan_harian (status pending)
   → Verifikasi supervisor (approve / reject / pending)
   → Output: laporan keuangan (buku besar, mutasi nasabah, saldo per produk,
             laporan tahunan), ekspor PDF/Excel, rekonsiliasi kas
```

**Alur 3 — Alur data sekunder:** reset password/PIN (permintaan → verifikasi identitas → generate OTP → kirim email SMTP → validasi OTP → ubah kredensial) dan backup (baca basis data → salin ke `storage/app/backups` → daftar berkas untuk pemulihan manual).

Pada setiap alur, data bergerak searah dari sumber (*source*: input pengguna) melalui aktivitas pengolahan (*transform*) menuju tujuan (*sink*: basis data, struk, laporan, notifikasi), sesuai konsep arsitektur aliran data: *input → processing → output*.

## 7. *Operating Systems*

Sisi perangkat lunak sistem operasi yang menopang rancangan ini:

1. **Sistem operasi server:** aplikasi Laravel bersifat **portabel** dan dapat dijalankan pada Windows maupun Linux (Ubuntu/Debian) selama kebutuhan runtime (PHP, ekstensi, web server, MySQL) terpenuhi. Skrip `jalankan-server.bat` disediakan untuk menjalankan server pada lingkungan pengembangan Windows di sekolah (`php artisan serve`).
2. **Runtime aplikasi:** PHP 8.3 dan Laravel 13 (plus Sanctum 4) — *platform independent*, tidak terikat satu OS tertentu.
3. **Sistem operasi klien:** PC teller/supervisor/admin cukup dengan **OS apa pun yang memiliki *web browser*** modern (Windows/Linux/ChromeOS) karena sifat *thin client* berbasis web; nasabah memakai Android/iOS pada aplikasi mobile yang berkomunikasi via REST API.
4. **Layanan OS pendukung:** layanan basis data MySQL & folder `storage/app/backups`, layanan jaringan (LAN sekolah/Wi-Fi) untuk koneksi klien–server, dan layanan SMTP (mail server) untuk pengiriman OTP.
5. **Pertimbangan pemilihan OS:** Windows dipilih untuk lingkungan pengembangan/sekolah agar mudah dijalankan tanpa konfigurasi server rumit; untuk produksi **disarankan** Linux agar keamanan, stabilitas, dan performa lebih terjaga. Struktur aplikasi yang hanya membutuhkan web server + PHP + DBMS membuat perpindahan antar OS tidak memerlukan perubahan kode.

**Catatan:** dukungan lintas sistem operasi dijelaskan sebagai rancangan, bukan klaim hasil pengujian pada setiap lingkungan.

## 8. Rancangan Arsitektur Perangkat Lunak

> *[Sisipkan gambar diagram arsitektur di sini. Sumber diagram tersedia pada `arsitektur-bankmini.dot` dan dirender dengan Graphviz.]*

**Penjelasan rancangan:**

1. **Arah aliran utama:** *Client* (browser & mobile) → route & middleware (autentikasi, otorisasi peran, status akun, pembatasan percobaan) → controller → service (logika bisnis) → model Eloquent → basis data MySQL; hasilnya kembali sebagai halaman Blade (web), respons JSON (API mobile), atau struk PDF.
2. **Gaya arsitektur:** utamanya **berlapis (layered/MVC)** dengan basis data sebagai pusat (**data-centered**). Karena **berlapis longgar**, controller boleh mengakses model langsung (garis putus-putus pada diagram) untuk kebutuhan sederhana, tanpa selalu melewati service.
3. **Keamanan:** jalur masuk difilter `auth:sanctum` + `RoleMiddleware` + `CheckActiveUser`/`EnsureActiveApiUser` + `throttle`; password disimpan dalam bentuk *hash*, **PIN nasabah divalidasi pada setiap transaksi** (`Hash::check`), dan setiap aktivitas penting tercatat di `activity_logs`.
4. **Konsistensi data:** penulisan saldo, transaksi, jurnal, dan audit log dilakukan dalam **satu transaksi database (ACID)** — bila gagal, seluruhnya *rollback*, sehingga tidak ada data setengah jadi.
5. **Layanan pendukung:** SMTP hanya dipakai untuk OTP dan backup disimpan ke folder `storage/app/backups`. Layanan ini bukan bagian wajib dari setiap alur transaksi, sehingga gangguan pada SMTP atau backup tidak menghentikan proses inti.
6. **Skalabilitas:** karena seluruh klien memakai basis data yang sama, penambahan klien baru cukup menambah perangkat (browser/HP) tanpa mengubah rancangan; bila beban meningkat, basis data dapat dipindah ke server terpisah tanpa mengubah kode aplikasi (cukup menyesuaikan konfigurasi koneksi).
